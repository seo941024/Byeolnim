# byeolnim.app

개인 사이드 프로젝트 웹앱. 배포 방법은 [`README_DEPLOY.md`](./README_DEPLOY.md) 참고.

## 기술 스택

- **Hosting / Serverless**: Vercel — 정적 자산 서빙 + `api/*.js` 서버리스 함수
- **Database**: Redis (Upstash) — 키-값 저장소, 시계열 스냅샷 및 세션 데이터 적재
- **Scheduling**: Vercel Cron — 인증된 배치 잡을 하루 1회 자동 실행
- **Frontend**: 바닐라 JavaScript / HTML / CSS, 번들러 없음
- **Auth**: 자체 세션 기반 인증 (Redis 저장)
- **Push**: Web Push API (VAPID)
- **PWA**: manifest + 설치 가능한 웹앱

## 아키텍처 — 외부 데이터 수집 파이프라인

공식 API가 없는 외부 서비스의 공개 엔드포인트를 조회해, 주기적으로 수집·
적재하고 조회 시점에 가공해 보여주는 **ELT(Extract → Load → Transform)**
구조를 구현했습니다.

```
[Extract]   서버(api/_lib.js)가 외부 공개 엔드포인트를 HTTP로 조회
                │
                ▼
[Load]      가공 없이 Redis에 시간순 스냅샷으로 그대로 적재
                │   (레코드당 최근 N개만 유지하는 롤링 버퍼)
                ▼
[Schedule]  Vercel Cron이 매일 1회 전체 대상을 재조회해 자동 적재
                │   (api/collect.js, 시크릿 기반 인증으로 외부 호출 차단)
                ▼
[Transform] 조회 API(api/history.js)가 서빙 시점에 구간별 변화량을 계산
                (저장 시점이 아니라 "꺼내 쓸 때" 가공 — ELT의 핵심)
```

**CORS 우회**: 브라우저가 외부 도메인을 직접 호출하면 CORS 정책에 막히므로,
서버가 중간에서 대신 호출하는 프록시 구조로 우회. 브라우저 ↔ 자체 서버는
같은 출처라 제약이 없고, 서버 ↔ 외부 서비스는 브라우저가 아니라 서버 간
통신이라 애초에 CORS 적용 대상이 아님.

**스케일 메모**: 레코드당 최대 180개 스냅샷 수준의 소규모 구조입니다.
ELT라는 용어 자체는 대용량 데이터 웨어하우스에서 쓰이는 게 일반적이라,
이 프로젝트는 "같은 패턴을 작은 스케일에 적용한 것"이라는 전제가 붙습니다.

## 기타 설계 메모

- **확률 시뮬레이션 모듈**: 가중치·천장(pity) 기반 확률 로직을 1차 소스
  문서와 대조 검증하며 구현. 추정치는 데이터 파일 주석에 명시하고 확정된
  값과 구분해서 관리.
- **프레임워크 미사용**: 번들러 설정 없이 배포 속도를 우선한 선택. 화면
  수가 늘면서 상태 관리가 분산되는 한계를 겪음 — 다시 설계한다면
  TypeScript + 컴포넌트 단위 상태 관리를 도입했을 것.
